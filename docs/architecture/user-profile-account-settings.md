# Stage 8 — User Profile & Account Settings (профиль и настройки аккаунта)

Статус: автоматическая регрессия и финальная Manual QA (8/8) пройдены 2026-10-18. Этот документ описывает фактический контракт Stage 8. Stage 7.9 Marketplace Licensing не меняется; требования к Production Deployment остаются в отдельном checklist (списке условий запуска).

## Модель данных и миграция

`user_profile_security_053` продолжает единственную Alembic chain (цепочку миграций) после `custom_block_trust_schema_repair_052`. Новые поля `users`: дата рождения, международный телефон и статус его подтверждения, ожидающий новый email, флаги обязательного подтверждения email и управляемой сервером сессии. Для существующих пользователей оба флага по умолчанию `false`; пустые новые поля не блокируют их вход. Новая регистрация ставит оба флага в `true`.

`users.id` остаётся внутренним стабильным ключом ownership (владения). `users.public_id` — отображаемый постоянный User ID (номер пользователя). `reserved_user_public_ids` резервирует выданные номера без повторного использования после удаления пользователя. Изменение имени записывается в `display_name_history`, доступ к истории через публичный API не предоставляется. `CustomBlock.owner_user_id`, опубликованные версии и выданные права не меняются; Marketplace показывает текущее `User.name` как Display Name (отображаемое имя) вместе с `@Username`, если ник уже выбран.

`account_action_tokens` хранит только SHA-256 hash (хеш) случайного одноразового токена, назначение, адрес и срок действия. `account_sessions` — серверный реестр сессий. `user_totp` хранит зашифрованный TOTP secret (секрет приложения для кодов); `totp_backup_codes` содержит только HMAC-хеши резервных кодов. `security_audit_events` фиксирует типы событий без токенов, паролей и содержимого писем. `account_deletion_requests` хранит статус запроса на удаление.

## Регистрация и юридические согласия

`POST /auth/email/register` принимает `name`, `username`, `email`, `password`, `date_of_birth`, `legal_revision_ids` и три отдельные отметки: `terms_accepted`, `privacy_acknowledged`, `personal_data_consent_accepted`. Backend считает возраст календарно на текущую дату и отклоняет регистрацию до 18 лет. Требуются опубликованные версии `public_offer` (публичная оферта), `privacy_policy` (политика обработки персональных данных) и `personal_data_consent` (отдельное согласие на обработку персональных данных); сервер сверяет ID с актуальными редакциями и записывает три отдельные записи `Consent` с источником `registration` в одной транзакции создания аккаунта. Для политики фиксируется `acknowledged`, для оферты и отдельного согласия — `accepted`. `advertising_consent` (необязательное рекламное согласие) регистрацией не требуется и не создаётся. Если обязательные редакции не опубликованы, регистрация недоступна. Номера версий этих трёх документов берутся из опубликованных редакций юридической CMS (системы управления документами), а не зашиты в код; `1.0` в тестах — изолированные тестовые редакции. Утверждённые production-версии нельзя установить без конфигурации production и юридического решения. Обязательность отдельного согласия и формулировки отметок требуют юридического согласования.

В Development DB опубликованы `public_offer` 1.2, `personal_data_consent` 1.0 и явно тестовая `privacy_policy` `DEV-TEST-20261010` (ID 5). Она служит только локальной проверке; Production не принимает редакции `DEV-TEST-` как действующие и запрещает создавать или публиковать их. Проверка обязательных отметок и запись согласий остаются обычными. Юридически утверждённая политика для Production ещё нужна; это `PROD-BLOCKER-01` в [Production Readiness Checklist](../operations/PRODUCTION_READINESS_CHECKLIST.md). Технические тесты используют отдельную базу и явно тестовые документы. Рабочие SQLite-соединения включают проверку FK (внешних ключей) при открытии; история исправления единственной старой осиротевшей строки и архив приведены в `docs/operations/migrations.md`.

Результат регистрации не содержит access token (токен доступа). Демоконтент до подтверждения email не создаётся. Переходные аккаунты могут дополнить дату рождения в профиле без автоматической блокировки.

## Email Verification (подтверждение электронной почты)

Случайный токен действует 24 часа, связан с пользователем и точным адресом. Предыдущий действующий токен того же назначения инвалидируется при новой выдаче. Ссылка содержит токен во фрагменте URL (`#token=...`), который браузер не передаёт в HTTP-запросе страницы. Frontend удаляет фрагмент из адресной строки, вызывает `POST /auth/email/verify-preview` для проверки ссылки и ждёт отдельного нажатия пользователя. Только `POST /auth/email/verify` атомарно расходует токен и меняет подтверждение адреса. Повторное применение и истёкший токен получают ошибку. Подтверждение не создаёт сессию, поэтому ссылка работает и в другом браузере.

`POST /auth/email/resend-verification` отвечает одинаково для чужого или отсутствующего адреса; есть лимиты по IP и адресу и пауза 60 секунд. `POST /auth/email/correct-email` позволяет исправить адрес нового неподтверждённого аккаунта после проверки пароля и инвалидирует старую ссылку исходного адреса. До подтверждения Backend не выдаёт сессию и не принимает старый неподтверждённый JWT. Старые пользователи сохраняют вход, но могут запросить подтверждение адреса для перехода с OAuth (входа через внешнего провайдера).

В development Vite отдаёт React SPA (одностраничное приложение) для прямых GET-переходов на `/auth/verify`, `/auth/verify-pending`, `/auth/two-factor`, `/auth/reset` и страницы `/legal/:slug`; запросы `/legal/documents`, `/legal/consent`, `/legal/account`, `/legal/archive` и `/legal/doc*` остаются API proxy к Backend. API POST и OAuth-маршруты `/auth/*` также идут в Backend. Production reverse proxy (обратный прокси) должен применять такое же разделение маршрутов. Playwright smoke проверяет прямые переходы, юридическую страницу, мобильную ширину 390 px, подтверждение только по нажатию и обработку истёкшей ссылки.

`POST /api/user/security/change-email` требует действующий пароль. Старый адрес остаётся основным до подтверждения нового. После подтверждения отзываются сессии и прежние JWT, событие пишется в security audit (журнал событий безопасности), а уведомления старого адреса ставятся в существующий Notification Outbox (очередь уведомлений). Новый адрес должен быть свободен.

Регистрационное письмо отправляется через существующий `email_transport` после формирования нейтрального HTTP-ответа в FastAPI BackgroundTasks (задаче после ответа); одноразовый токен остаётся только в памяти задачи и в виде хеша в БД. Отдельная почтовая система и outbox для одноразовой ссылки не создаются. Сбой SMTP не превращает ответ регистрации в признак существования адреса: новый аккаунт сохраняется без активной ссылки, пользователь может запросить повторную отправку после cooldown (паузы). Задача после ответа не является долговечной очередью: при падении процесса письмо может потеряться, и потребуется повторный запрос. API не утверждает фактическую доставку; `smtp_accepted` не возвращается. Проверка наличия письма и наблюдение за SMTP обязательны для развёртывания. Development/Test без SMTP использует `LoggingEmailTransport`, который не доставляет письмо и не логирует токен. Для локального QA `scripts/dev-stage8-qa.ps1` запускает ограниченный loopback SMTP-приёмник (сервер приёма тестовой почты) на `127.0.0.1:1025` с просмотром писем на `http://127.0.0.1:8025/` и штатный Backend с SMTP-настройками процесса. Письма не пересылаются вовне. Остальные Auth emails (письма восстановления и смены адреса) сохраняют существующий синхронный контракт. Security notifications (уведомления безопасности) используют существующий Notification Outbox (очередь уведомлений) с retry (повторной попыткой); worker (обработчик очереди) должен быть запущен отдельно. `PROD-BLOCKER-02` в [Production Readiness Checklist](../operations/PRODUCTION_READINESS_CHECKLIST.md) требует реального провайдера, отправителя, публичный HTTPS-адрес, DNS-политики почты и запущенный worker. Реальная Production-почта здесь не использовалась.

В локальной Manual QA `scripts/dev-stage8-qa.ps1` теперь запускает отдельный Notification Outbox worker (обработчик очереди) вместе с Backend. Скрипт проверяет выбор SMTP transport (транспорта отправки) и очищает учётные данные SMTP только в окружении локального процесса. Пустой `SMTP_HOST` в `backend/.env` при отдельном запуске `scripts/dev-backend.ps1` оставляет письма в режиме записи факта в лог; работающий почтовый приёмник сам по себе настройку Backend не меняет.

## Пароль, сессии и 2FA

Новые пароли хешируются PBKDF2-SHA256 с 310000 итерациями; прежние PBKDF2/bcrypt хеши продолжают проверяться. `POST /auth/email/request-reset` не раскрывает существование аккаунта и выдаёт ссылку только на подтверждённый адрес. `POST /auth/email/reset` расходует одноразовый токен, заменяет пароль и отзывает сессии. `POST /api/user/security/change-password` требует старый пароль и также отзывает сессии.

Ссылка восстановления действует 24 часа по UTC. Повторный запрос заменяет прежнюю ссылку только после принятия нового письма SMTP-сервером: при сбое передачи транзакция откатывается, а прежняя неиспользованная ссылка остаётся действительной до своего срока. Нейтральный ответ запроса не подтверждает существование аккаунта и не гарантирует доставку в ящик. Лимит — пять запросов с одного IP или для одного адреса за десять минут; следующий запрос получает HTTP 429 и не создаёт письмо. Открытие страницы, GET и клиентская ошибка несовпадения паролей токен не расходуют. Успешный сброс делает ссылку одноразово использованной, отзывает прежние сессии и требует нового входа. В письмах и обычных логах токен не сохраняется; проверяется только его хеш в БД.

Изолированный Chromium regression (браузерный тест) `frontend/tests/e2e/stage8-password-reset-isolated.spec.ts` использует `scripts/qa-stage8-reset-isolated.py`: скрипт выбирает новую SQLite DB только в `qa_artifacts`, применяет миграции к ней, создаёт синтетический подтверждённый аккаунт и запускает временный API на 127.0.0.1:18001 с локальным SMTP на 127.0.0.1:1025. Для теста нужны работающий Frontend 5173 и локальный приёмник 8025; Playwright запускается с `QA_RESET_BACKEND=1` и `QA_FRONTEND_URL=http://127.0.0.1:5173`. Development DB скрипт не открывает. После теста временный API останавливают; тестовые базы остаются в игнорируемых Git QA-артефактах.

Access JWT (токен доступа) содержит `sid`, ссылающийся на `account_sessions`. Общая dependency (проверка доступа) валидирует подпись, версию токена, существование активной сессии и подтверждение email для новых аккаунтов. `GET /api/user/security/sessions`, `DELETE /api/user/security/sessions/{id}` и `POST /api/user/security/sessions/revoke-others` управляют своими сессиями. Старые JWT без `sid` живут до естественного истечения только для переходных аккаунтов без `session_required`; после нового входа управляемая сессия становится обязательной. Отдельного refresh token (токена обновления) в текущей архитектуре нет.

TOTP (одноразовые коды приложения): setup (подключение) требует пароль, confirm (подтверждение) проверяет первый код, после чего секрет хранится зашифрованным с ключом, полученным из backend JWT secret. Резервные коды показываются один раз и хранятся HMAC-хешами. При входе пароль выдаёт короткий challenge (запрос второго фактора), не полноценную сессию. Только `POST /auth/email/complete-2fa` с валидным TOTP или резервным кодом создаёт сессию; повторное использование кода и challenge отклоняется. Отключение требует пароль и код. Смена backend JWT secret сейчас также делает существующие TOTP secrets недоступными: перед ротацией требуется отдельная процедура переупаковки ключа.

Существующие Google/Yandex/Mail.ru связи и Backend OAuth (вход через внешнего провайдера) сохраняются; новые OAuth-регистрации запрещены. Кнопки этих провайдеров убраны из пользовательского интерфейса входа. Старые пользователи могут подтвердить почту и установить пароль через восстановление; для пользователей с TOTP OAuth callback (возврат после внешнего входа) требует второй фактор. Перед развёртыванием необходимо проверить переход реальных OAuth-аккаунтов, поскольку отсутствие таких аккаунтов в Development DB не доказывает их отсутствие в других средах.

## Профиль и конфиденциальность

`PATCH /me` меняет отображаемое имя и дату рождения без передачи ownership. `PUT/DELETE /me/phone` нормализует международный номер в E.164; без SMS-провайдера статус остаётся неподтверждённым и номер не является фактором восстановления. `POST/DELETE /me/avatar` проверяет MIME type (тип файла) и фактический формат, размер и разрешение, преобразует картинку в PNG без исходных метаданных, использует случайное имя и удаляет старый файл после успешного сохранения.

Раздел уведомлений показывает обязательные категории без фиктивных переключателей. Необязательное рекламное согласие управляется через `/privacy/optional-consents`; новая запись принятия или отзыва сохраняет версию документа, а актуальный юридический статус не считает отозванное согласие действующим. Фактическая рассылка рекламы в Stage 8 не добавляется.

Из «Настройки → Конфиденциальность» ссылка ведёт на существующий маршрут `/dashboard/account/legal`. Страница получает действующие и архивные редакции, а также полную историю собственных согласий через защищённый `GET /legal/account`. Поле `accepted` сохраняет прежний контракт последних действующих согласий; `consent_history` возвращает все записи в обратном хронологическом порядке, включая отзывы, версию, результат и дату. Данные другого пользователя, IP-адреса и user-agent не выдаются. Ссылка у записи с редакцией открывает точную версию документа; прямой переход и обновление страницы обслуживаются React Router (маршрутизатором React).

Из кабинета ссылки на конкретные документы используют `/dashboard/account/legal/:slug` и `/dashboard/account/legal/:slug/v/:version`: те же React-компоненты остаются внутри `DashboardLayout` (структуры личного кабинета), включая боковое меню и возврат к истории. Публичные `/legal/:slug` и `/legal/:slug/v/:version` используют те же компоненты без обязательного входа. После F5 на защищённом маршруте `AuthGate` восстанавливает пользователя через `/me`. На публичном маршруте Header (верхнее меню) при наличии сохранённого токена передаёт переход в кабинет `AuthGate`, который проверяет `/me`; просроченный токен не даёт доступ к кабинету. Срок жизни JWT и серверная сессия этим изменением не меняются.

`POST /privacy/export` выдаёт данные владельцу аккаунта. `POST /privacy/delete` требует пароль (и TOTP при включении) и создаёт идемпотентный запрос `pending_review` (ожидает рассмотрения). Он не стирает пользователей, Marketplace, лицензии, платежи и аудит. Владелец платформы через `GET /privacy/admin/deletion-requests` просматривает очередь до 100 последних запросов и через `POST /privacy/admin/deletion-requests/{id}/review` ставит `in_review`, `needs_information` или `awaiting_legal_policy`; каждое изменение статуса журналируется для администратора и заявителя. Другим пользователям эти маршруты возвращают 403. Статус виден заявителю в разделе конфиденциальности. Ни один статус не означает фактического удаления. Операционный порядок: проверить личность и зависимости, определить требования хранения и связаться с заявителем по защищённому каналу; при отсутствии утверждённой политики поставить `awaiting_legal_policy`. Сроки хранения и финальный процесс исполнения удаления требуют юридического утверждения. Старое немедленное стирание выключено из пользовательского маршрута.

## Границы безопасности и тестирования

Критические операции требуют backend auth (проверку личности), ограничение частоты и проверку текущего пароля/второго фактора где нужно. Production auth throttling (ограничение попыток) использует Redis с fail closed (запретом операции при недоступности Redis); development/test использует память процесса. Для изменяющих запросов с cookie в production проверяется `Origin` (источник запроса); bearer запросы продолжают использовать токен в заголовке. Токены, TOTP secret и пароли не пишутся в обычный audit payload (поля журнала).

Pytest в `backend/tests/conftest.py` и корневом `tests/conftest.py` использует отдельные тестовые SQLite БД и применяет миграции к ним; Development DB не служит тестовой базой. `test_stage8_migration.py` проверяет upgrade/downgrade на ещё одной временной БД. `test_stage8_email_delivery.py`, `test_stage8_dev_qa.py` и `test_stage8_local_mailbox.py` проверяют локальную SMTP-передачу, юридическое разграничение Development/Production и отказ Production от тестового транспорта без внешних писем. `frontend/tests/e2e/stage8-browser-smoke.spec.ts` запускает Chromium с подменёнными API-ответами для проверки клиентских маршрутов и адаптивности. `frontend/tests/e2e/stage8-final-real.spec.ts` проходит в настоящем Chromium на Development DB revision 054 с отдельным тестовым аккаунтом и локальной почтой: регистрация 18+, юридические условия и согласия, письмо и подтверждение email, вход и `/me`, сохранение профиля и телефона после F5, аватар, экспорт, юридические страницы и история согласий, сессии, отмена незавершённой настройки TOTP, полноценное включение TOTP, вход с резервным кодом и отказ повторного использования, отключение TOTP с отзывом сессии, мобильная ширина 390 px и восстановление пароля с повторным входом. Это не проверка утверждённых юридических документов или Production SMTP/Redis/PostgreSQL.

## Final Security & UX Stabilization

Настройки используют параметр `?tab=profile|security|notifications|privacy`; прямая ссылка, F5 и история браузера восстанавливают выбранный раздел. Пароли разных операций хранятся в отдельных полях React и очищаются после ответа, при смене раздела и размонтировании компонента. Браузерный менеджер паролей может предлагать сохранённый пароль в поле смены пароля; Backend всё равно проверяет его повторно.

`POST /api/user/security/totp/setup` после проверки текущего пароля создаёт новый pending secret (ожидающий подтверждения секрет), показываемый через локально сформированный QR и скрытый по умолчанию ключ. `POST /api/user/security/totp/cancel` удаляет только неподтверждённую настройку. Повторный запуск заменяет прежний ключ, а старый код больше не подтверждает настройку. Действующий TOTP записью cancel не затрагивается. После подтверждения Backend отзывает текущие сессии, резервные коды показываются один раз.

Вход через основное окно содержит восстановление по подтверждённой почте через существующие `/auth/email/request-reset` и `/auth/email/reset`. Выгрузка `/privacy/export` отдаёт профиль, согласия, метаданные ботов, сохранённые сообщения, агрегаты событий и настройки без паролей, токенов и TOTP секрета; файл содержит личные данные и должен храниться защищённо.

Локальный SMTP-приёмник по адресу 127.0.0.1:1025 подтверждает только техническую доставку Development. Доставка в Mail.ru и другие внешние ящики не считается проверенной без отдельного реального теста с настроенным Production-провайдером.

## Public Username, identity and security notices

`user_identity_054` (миграция публичного ника) следует после 053 и добавляет nullable `users.username` и уникальный `users.username_key`. У существующих аккаунтов оба поля остаются пустыми до самостоятельного выбора. `POST /auth/email/register` теперь требует ник; `GET /auth/email/username-availability` даёт предварительную проверку с ограничением частоты, а `POST /me/username` позволяет прежнему пользователю выбрать ник один раз. Конкурентное сохранение разрешает уникальное ограничение БД; второй запрос получает 409. Смена ника обычным пользовательским API отсутствует. Вход остаётся по email.

Проверка 054 и браузерные сценарии выполнялись на отдельных временных SQLite БД. Development DB по последнему подтверждённому состоянию остаётся на 053; перед ручной проверкой нового ника на ней нужен отдельно разрешённый backup и upgrade 053 → 054. Backend с новой моделью не следует направлять на схему 053.

Политика в `backend/services/usernames.py`: 3–30 символов; NFC (нормализованная видимая форма) и NFKC casefold (ключ уникальности без регистра); латинские **или** кириллические буквы в одном нике, ASCII-цифры, `_`, `-`, точка. Смешение двух алфавитов, невидимые/управляющие и совместимые символы, пробелы, emoji, точки подряд и системные имена отклоняются. Ники на обычной кириллице и латинице разрешены. Это защита от простых смешанных написаний, а не полная детекция всех визуальных омографов.

Marketplace продолжает хранить авторство по `User.id`, выводит текущее Display Name (отображаемое имя) и `@Username`. Версии, grants (выданные права) и лицензии не переписываются. Контакты и сообщения внутреннего чата также связаны через `User.id`; в выборе собеседника и карточке доступны имя, ник и публичный User ID. Email другого пользователя не входит в краткий профиль чата.

Скрытые поля паролей имеют независимый переключатель видимости; состояние закрывается с размонтированием формы. Короткие одноразовые TOTP-коды вводятся открыто, чтобы пользователь мог проверить цифры; TOTP secret (секрет приложения) отдельно скрыт до явного показа. Значения не передаются при нажатии на значок глаза. Атрибуты autocomplete разделяют текущий и новый пароль; браузерный менеджер паролей может применять собственные эвристики.

`login` ведёт единый отказ 401 для неизвестного адреса и неверного пароля и проверяет dummy hash (фиктивный хеш) для отсутствующего аккаунта. После четырёх неверных попыток для существующего аккаунта за десять минут создаётся не более одного обязательного письма в сутки. Уведомление не означает доказанный взлом. Очередь использует детерминированный ключ идемпотентности для этого события; лимит по IP и адресу ограничивает повторные попытки. Смена/восстановление пароля, смена email и включение/отключение TOTP продолжают создавать обязательные события в существующем Notification Outbox (очереди уведомлений), включая оба адреса после завершённой смены email. Письма содержат время UTC, тип события и безопасный совет, без паролей, токенов и секретов. Сбой SMTP обрабатывается повторными попытками outbox и не отменяет уже безопасно завершённое изменение аккаунта.

Регистрация нового и уже занятого email возвращает одинаковый нейтральный HTTP 200 без признака фактической доставки. Занятый адрес не создаёт второй аккаунт, ссылку или уведомление. Проверка ника и ограничение частоты работают до этого ветвления. Минимальное время ответа 500 мс вместе с отправкой SMTP после HTTP-ответа уменьшают различия во времени; абсолютного доказательства неразличимости под любой нагрузкой нет. Rate limiting (ограничение частоты) по IP и адресу действует в Development/Test в памяти процесса, в Production — через Redis с отказом при недоступности Redis. Лимит по адресу может временно ограничить действия владельца после чужих массовых попыток. Эти ограничения остаются частью проверки безопасности перед Production.

Действующий `account_sessions` хранит User-Agent и время активности, но User-Agent не является достоверным идентификатором устройства. Поэтому автоматическое письмо «новое устройство» не отправляется: надёжное распознавание требует отдельного привязанного к сессии доверенного устройства, правил приватности, срока жизни и защиты от подмены. Существующий статус чата также не является достоверным presence (присутствием в сети). Эти ограничения нельзя описывать пользователю как реализованное обнаружение нового устройства.
