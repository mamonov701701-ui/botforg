# Database Migration Chain (цепочка миграций БД)

Current single Alembic head: `user_identity_054`. Development DB обновлена с `user_profile_security_053` до `user_identity_054` 2026-10-12 после проверенной резервной копии и пробы миграции на восстановленной копии.

Development DB на 2026-10-10 находится на 053. Историческая осиротевшая `scenario_versions.id=373` → отсутствующий `scenarios.id=61` удалена по отдельному разрешению владельца: перед удалением все 127 таблиц совпали с проверенной копией 053, полная запись сохранена в `qa_artifacts/db_backups/scenario_version_373_archive_20261010T063715Z.json` с проверенным SHA-256 `bdcd923d7871875c15f8771dd314f0d13c5681ff8020cdf1564e6aac27f6f5d0` (рядом файл `.sha256`). Изолированное восстановление записи из архива прошло проверку. Удаление одной строки выполнено в транзакции; после него `PRAGMA integrity_check = ok`, `PRAGMA foreign_key_check` пуст, revision = 053, все прочие сценарии и версии совпадают с копией до исправления. Не восстанавливайте строку в рабочую БД без действительного родительского сценария: это снова создаст нарушение FK. Проверенная копия состояния 052 создана SQLite Backup API в `qa_artifacts/db_backups/botforg_pre_stage8_fk_investigation_20261009T141911Z.db`. Изолированная копия прошла upgrade 052 → 053 → downgrade 052 → upgrade 053 без изменения количества пользователей и сценариев; нарушение FK тогда сохранялось. Не использовать downgrade 053 как откат данных Stage 8.

После upgrade проверенная копия 053 сохранена в `qa_artifacts/db_backups/botforg_after_053_20261010T055233Z.db`. Значения во всех 118 таблицах, существовавших до миграции (кроме служебной `alembic_version`), совпали с копией 052 при сравнении по исходным столбцам. Перед публикацией тестовой политики создана дополнительная проверенная копия SQLite Backup API (средствами SQLite): `qa_artifacts/db_backups/botforg_pre_dev_test_privacy_20261010T075942Z.db`, SHA-256 `1e5b2f23a9618a5e847bfb77f25ab4e68b627ee5ec5e7381fa1028b29e2e88a3`. В Development DB опубликованы `public_offer` 1.2, `personal_data_consent` 1.0 и явно тестовая `privacy_policy` `DEV-TEST-20261010` (ID 5). Последняя разрешает только локальную проверку регистрации и не является юридически утверждённой.

Рабочий SQLite engine (движок соединений) в `backend/database.py` включает `PRAGMA foreign_keys=ON` при открытии каждого соединения; регрессионный тест проверяет реальное отклонение осиротевшей строки. До этого SQLite по умолчанию не проверял FK на рабочих соединениях, что могло позволить появление исторического нарушения; точный момент и операция его возникновения не установлены. Alembic использует отдельное соединение для структурных миграций, поэтому целостность проверяется отдельно до и после upgrade.

Для Production (рабочей среды) нужны три **юридически утверждённые опубликованные** редакции: `public_offer` (публичная оферта), `privacy_policy` (политика обработки персональных данных), `personal_data_consent` (отдельное согласие на обработку персональных данных). После утверждения текста администратор создаёт черновик через существующую юридическую CMS (систему управления документами) или `POST /api/admin/legal/revisions`, проверяет содержание и публикует через `POST /api/admin/legal/revisions/{id}/publish`. Тестовые версии с префиксом `DEV-TEST-` и пометкой `[DEV TEST]` в заголовке и тексте допустимы только в Development. Production отвергает их создание и публикацию, не считает опубликованную тестовую редакцию действующей для регистрации и исключает её из публичного списка документов. Утверждение и публикация настоящей политики остаются обязательным условием запуска: [Production Readiness Checklist](PRODUCTION_READINESS_CHECKLIST.md).

Файл `docs/legal/privacy_policy_ru.md` и legacy-маршрут `/legal/doc/privacy_policy` существуют отдельно от опубликованных редакций CMS; они не удовлетворяют серверному условию регистрации.

Для локальной проверки `scripts/dev-stage8-qa.ps1` запускает локальный SMTP-приёмник (сервер приёма тестовой почты) на `127.0.0.1:1025`, показывает письма на `http://127.0.0.1:8025/` и запускает Backend штатным `scripts/dev-backend.ps1` с временными SMTP-настройками процесса. Письма не уходят в интернет; транспорт сообщает о принятии SMTP-приёмником, а не о доставке в реальный ящик. Frontend отдельно запускается из `frontend` командой `npm.cmd run dev`. В Production обязателен настоящий почтовый провайдер; тестовый приёмник не используется.

## `user_identity_054`

Продолжает 053: добавляет nullable `users.username` и `users.username_key` с уникальным ограничением для регистронезависимого ключа. Существующим пользователям ник автоматически не назначается; все их прежние связи и права остаются по `users.id`. SQLite upgrade/downgrade проверены на отдельной временной БД. Для Development DB создана согласованная SQLite Backup API копия `qa_artifacts/db_backups/botforg_pre_user_identity_054_20261012T162923Z.db`, SHA-256 `ad0804212aab73da138d26ce277ca5889913ee220ae1741e1f0d568427bbc468`. Восстановление и upgrade копии прошли; в рабочей DB после upgrade `integrity_check=ok`, `foreign_key_check` пуст, revision 054. Хеши строк всех прежних таблиц совпали, у `users` совпали все исходные столбцы; количества: 33 пользователя, 66 сценариев, 393 версии сценариев, 7 Custom Blocks, 13 версий и 5 Marketplace listings (публикаций). Перед миграцией не обнаружен активный writer (пишущий процесс). Для отката состояния данных используйте проверенный backup, а не Alembic downgrade.

Для последующих обратимых Dev DB миграций требуются проверка текущей revision и единственного head, целостность и FK, согласованный backup с проверкой восстановления, изолированная проба upgrade и сверка данных после применения. Разрушительные или неподтверждённо обратимые изменения, удаление данных и Production DB требуют отдельного разрешения. Если действующий `AGENTS.md` требует явного разрешения Dev DB миграции, соблюдайте это более приоритетное правило; данная 054 миграция была прямо разрешена владельцем.

## `user_profile_security_053`

Продолжает 052: добавляет совместимые nullable поля профиля, флаги обязательной проверки email и серверной сессии, таблицы одноразовых токенов, сессий, истории имени, запросов удаления, аудита безопасности, TOTP и резервных кодов. Существующие аккаунты сохраняют доступ без новых обязательных полей; новые регистрации включают строгий режим. Public User ID (публичный ID пользователя) резервируется на весь срок базы и не переиспользуется. Upgrade/downgrade проверен на изолированной SQLite базе; downgrade удаляет данные новых таблиц и не является операционным откатом.

## `custom_block_trust_schema_repair_052`

Repair migration после `custom_block_free_paid_trust_051`: в development SQLite ревизия 051 была записана, но таблица `trust_safety_reports` и её индексы отсутствовали. 052 проверяет объекты схемы 051, создаёт только отсутствующие таблицы/индексы и nullable price columns, а корректные объекты и данные не пересоздаёт. Некорректная структура существующей таблицы вызывает ошибку для отдельного разбора. Downgrade 052 возвращает только revision marker на 051: удалять объекты, принадлежащие 051, или их данные при таком откате нельзя. Миграция 051 остаётся неизменной.

## `ai_credit_ledger_040`

Создаёт AI credit ledger, buckets и debit allocations для grant/debit/expiry/revoke audit trail. Данные не мигрируются в spendable balance этой migration: opening grants выполняет отдельная идемпотентная cutover command. Downgrade удаляет эти таблицы; это разрушительно для ledger data и не является operational rollback plan.

## `legacy_plan_codes_to_current_041`

Нормализует `users.plan_code`: `free → start`, `pro → business_pro`, `developer → team`. Она затрагивает historical metadata, а не создаёт entitlement. Unknown non-empty legacy code вызывает fail-closed migration error, а не silent mapping. Downgrade возвращает только известные mappings; он не может восстановить исходное различие legacy значений после нормализации.

Development использует SQLite. Production target — PostgreSQL, но полная readiness для текущих 040/041 не заявляется без отдельного PostgreSQL gate. Перед upgrade необходимы backup, проверка revision chain и отсутствие неизвестных legacy codes.
