# Custom Block Review Workflow (процесс проверки)

## Scope and authority (область и полномочия)

Review (проверка) выполняется отдельно для каждой точной `CustomBlockVersion` (версии кастомного блока). Отчёт AI Security Agent (ИИ-агента безопасности) имеет только рекомендательный характер: он не может одобрить или опубликовать версию. Решение Manual Admin Review (ручной проверки администратором) может принять только уполномоченный администратор платформы с ролью `owner`, `admin` или установленной ролью BF Administrator.

## State diagram (схема состояний)

`draft` → Automated Validation (автоматическая валидация) → AI Security Agent (ИИ-агент безопасности) → `admin_review_pending` → `approved` / `needs_changes` / `rejected`

Если AI Security Agent не может вернуть корректный отчёт, версия переходит в `security_review_failed`. Её нельзя одобрить или опубликовать. После восстановления провайдера автор изменяет Draft (черновик), возвращая его в `draft`, и отправляет версию повторно.

Опубликовать можно только состояние `approved`. Реальное изменение проверяемого содержимого возвращает неопубликованную версию в `draft`; идентичный Auto-save (автосохранение) или сохранение только текущего шага Wizard (мастера) не сбрасывает проверку. Предыдущие отчёты, решения и события не удаляются. Новая версия начинается с `draft` и никогда не наследует одобрение родительской версии.

## Admin procedure (действия администратора)

1. Откройте **Управление блоками** и найдите версию в Admin Review Queue (очереди ручной проверки).
2. Сверьте номер версии, Stable Key (стабильный ключ) и для JavaScript — Artifact Hash (хеш артефакта).
3. Изучите Automated Validation (автоматическую валидацию) и структурированный отчёт AI Security Agent: находку, место, причину, серьёзность и рекомендацию. Статические проверки контракта относятся к Automated Validation, а не к ИИ-анализу.
4. Выберите **Одобрить**, **Нужны изменения** или **Отклонить**. Для изменений или отказа добавьте понятный и безопасный комментарий.
5. Одобрение открывает автору возможность публикации, но не публикует версию автоматически.

Review History (история проверки), отчёты, решения и события `CustomBlockReviewEvent` являются append-only records (записями только для добавления). События сохраняют предыдущее и итоговое состояние, участника, точный Artifact Hash и безопасные метаданные. Archive (архивирование) нельзя использовать как Security Revocation (отзыв по безопасности): архив запрещает новые вставки, но сохранённые сценарии с точной версией продолжают работать. Отзыв по безопасности — отдельный будущий процесс.

## Author and administrator meanings (значения для автора и администратора)

- **Черновик**: автор может редактировать и отправить версию на проверку.
- **На проверке**: версия находится в очереди администратора; повторная отправка и обычные действия проверки черновика скрыты.
- **Одобрен**: автор может отдельно опубликовать версию. Одобрение никогда не публикует её автоматически.
- **Нужны изменения**: комментарий администратора объясняет, что исправить. Реальное изменение начинает новый цикл проверки, сохраняя историю.
- **Отклонён**: текущий цикл завершён без публикации. Исправленный Draft можно отправить новым циклом.

Отчёт AI Security Agent носит рекомендательный характер. Решение уполномоченного администратора в Manual Admin Review является финальным для текущего цикла.

## Developer contract (контракт разработчика)

`POST /blocks/custom/{id}/submit-review` запускает серверную Automated Validation, затем границу AI Security Agent. `GET /blocks/custom/admin/review-queue` возвращает Admin Review Queue. `POST /blocks/custom/{id}/admin-review` требует административный RBAC (разграничение прав доступа). `POST /blocks/custom/{id}/publish` работает fail-closed (с безопасным отказом), если для текущего точного Artifact Hash нет успешного отчёта и решения `approved`. Development/test agent (агент разработки/тестирования) — только детерминированная заглушка; Production требует проверенный адаптер. Состояние Frontend используется только для отображения, а переходы всегда проверяет Backend.

Provider Boundary (граница провайдера) — интерфейс `CustomBlockSecurityAgent` в `backend/services/custom_block_security_agent.py`. Production adapter (боевой адаптер) должен возвращать тот же структурированный отчёт, безопасно отказывать без утечки секретов и выбираться через `CUSTOM_BLOCK_SECURITY_AGENT_PROVIDER`; права публикации он не получает. Тесты должны охватывать отправку, недоступность провайдера, RBAC очереди, каждое ручное решение, сброс после реального изменения, сохранение review при идентичном Auto-save, публикацию точного артефакта и отсутствие наследования новой версией.

Migration (миграция) `custom_block_review_workflow_045` создаёт версионную схему проверки. Repair Migration (восстанавливающая миграция) `custom_block_review_schema_repair_046` безопасно приводит раннюю Development DB, где 045 была применена до финальной формы, к канонической схеме: добавляет только отсутствующие поля отчёта, таблицу событий и индексы. Upgrade (обновление) идемпотентно для этого случая; Downgrade (откат) намеренно сохраняет схему, объявленную 045. Для применения repair нельзя сбрасывать Development или Production DB. Migration tests должны использовать изолированную тестовую БД.

## Known pre-production limitation

Mobile Responsive UI (мобильная адаптация интерфейса) при ширине около 390–400 px реализован частично. Desktop review UX (настольный интерфейс проверки) завершён; полная адаптация Platform UI — отдельный обязательный этап перед Production.
