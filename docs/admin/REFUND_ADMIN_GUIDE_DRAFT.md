# Руководство администратора: заявки на возврат

**DRAFT — не опубликовано, требует юридической проверки перед production.**

Версия черновика: 6.13 / 2026-07-18
Технический контур: `docs/TARIFFS_STAGE_6_13_REFUND_CONTRACT.md`

---

## 1. Назначение

Документ описывает работу уполномоченного администратора (owner / admin / BF Администратор) с заявками на возврат **после** реализации этапа 6.14. Сейчас это проект процесса; ручное изменение БД **запрещено**.

---

## 2. Карточка заявки

Администратор видит (без credentials / ciphertext / raw provider secrets):

- идентификатор заявки и revision;
- пользователь (id / маскированный email);
- CheckoutIntent / PaymentAttempt (сумма, валюта, продукт, статусы);
- категория причины (обязательная) и комментарий пользователя (если есть);
- **автоматический расчёт** (сумма, used/unused, entitlement action, даты);
- статус workflow;
- история revisions и audit;
- итоговое решение (после confirm).

---

## 3. Автоматический расчёт (утверждено)

### Тариф

Авто-расчёт **только** по точному времени:

- входы: `paid_amount`, `period_start` / `period_end`, момент calc, prior refunds;
- `recommended_refund = paid − time_used_portion − prior`, затем clamp в `[0, paid − prior]`;
- единое округление до копеек.

Система показывает сумму, time-used / unused, рекомендуемое entitlement action и даты.

### Addon (до per-addon ledger)

| Ситуация | Авто |
|----------|------|
| После покупки **нет** usage общего пула | Можно предложить **full** refund |
| После покупки **есть** usage общего пула | **`manual_review_required`** + показать доступные usage-данные |

**Запрещено** в UI и в решении утверждать, что pool usage «точно списан» с этого addon, пока нет ledger.

### После обязательного этапа ledger + FIFO

Авто-расчёт addon станет точным по `fifo_ledger_used(user_addon_id)`. Внедрение ledger+FIFO — **обязательный** следующий техэтап, не optional.

Авто-расчёт **нельзя затирать**: при правках сохраняется исходный snapshot; admin revision — отдельно. Дальше: final confirmation → refund → entitlement (без silent revoke / скрытых комиссий).

---

## 4. Допустимые поля редактирования (admin edit with reason)

| Поле | Можно |
|------|--------|
| Сумма возврата | Да, в пределах валидаций |
| Full ↔ partial | Да, если допустимо валидациями |
| Дата прекращения тарифа | Да |
| Объём отзываемого addon | Да (остаток ≥ 0); при pool usage — только в manual review с основанием |
| Entitlement action (whitelist) | Да |
| Запрос сведений / отклонение | Да |

При **любом** изменении обязательны:

1. категория основания корректировки;
2. текстовое обоснование;
3. сохранение исходного auto-calc и отдельной admin revision;
4. audit по изменённым полям;
5. ваш идентификатор и время;
6. новая revision.

---

## 5. Запрещённые действия

- Уменьшать сумму **без** категории и текста основания.
- Вводить скрытые штрафы / комиссии.
- Возвращать больше, чем `paid − prior_refunds`.
- Делать сумму &lt; 0.
- Допускать отрицательные остатки лимитов / addon.
- Повторно возвращать ту же сумму / повторно отзывать тот же entitlement.
- Silent revoke (менять доступ без отражения в решении и уведомлении пользователю).
- Одобрять **устаревшую** revision.
- Запускать refund до финального подтверждения.
- Править строки БД вручную (SQL / консоль) в обход API.
- Подтверждать заявку, по которой вы — тот же пользователь-плательщик, без эскалации (конфликт интересов).

## 6. Типичные validation errors

| Код (проект) | Смысл |
|--------------|--------|
| `refund_exceeds_cap` | Сумма &gt; max refundable |
| `refund_negative` | Сумма &lt; 0 |
| `stale_revision` | Revision устарела |
| `usage_fingerprint_mismatch` | Usage изменился с момента расчёта |
| `adjustment_reason_required` | Нет категории/текста при edit |
| `entitlement_already_revoked` | Повторный revoke |
| `refund_already_completed` | Повторный money refund |
| `confirm_required` | Попытка вызвать provider без confirm |
| `manual_review_incomplete` | Нет итогового ручного расчёта |

---

## 7. Повторное подтверждение (final confirm)

После approve / admin_edited заявка переходит в `awaiting_final_confirmation`.

Администратор ещё раз видит:

- итоговую сумму;
- последствия для тарифа/addon;
- основания корректировки (если были).

Только после confirm:

1. фиксируется неизменяемый decision snapshot;
2. отправляется refund провайдеру;
3. после confirmed refund применяется entitlement action;
4. пишется audit;
5. пользователь уведомляется.

---

## 8. Audit trail

Каждое значимое действие пишется в audit: кто, когда, какие поля (old→new), revision id, основание.
Raw секреты провайдера и полный webhook payload в админ-карточку **не** выводятся.

---

## 9. Конфликт интересов

Если администратор связан с аккаунтом заявителя (тот же user id / явная аффилиация):

- не подтверждать самостоятельно;
- эскалировать другому admin / owner;
- зафиксировать эскалацию в audit.

---

## 10. Эскалация спорных случаев

Передавать на эскалацию (второй администратор / юрист / продукт):

- chargeback;
- крупные суммы (порог — задать перед production);
- признаки злоупотребления;
- невозможность согласовать usage с деньгами;
- `provider_unknown` дольше согласованного SLA.

---

## 11. Порядок при `provider_unknown`

1. **Не** создавать второй refund «на всякий случай».
2. Запросить статус у провайдера (get payment/refund) по сохранённому id.
3. Дождаться webhook или однозначного API-статуса.
4. Entitlement **не** менять до подтверждённого refund (кроме отдельного согласованного playbook — не silent).
5. При `refund_failed` — новая попытка только с новым идемпотентным ключом после анализа причины.
6. Все шаги — в audit.

---

## 12. `manual_review_required` (в т.ч. addon с pool usage)

Типичный случай до ledger: addon + ненулевой общий usage после покупки.

1. Изучить доступные usage-данные и причину (`manual_review_required` / недостаток атрибуции).
2. **Не** утверждать точную привязку расхода к этому addon без ledger.
3. Сформировать итоговый расчёт вручную (сумма + объём отзыва + entitlement + даты) **с основанием**.
4. Остаток addon / лимитов ≥ 0; сумма в `[0, paid − prior]`.
5. Final confirm → refund → entitlement (audit + уведомление пользователю).

Без прохождения валидаций refund **не** выполняется.

---

## 13. Запрет ручного изменения БД

Любые правки статусов intent/attempt/subscription/addon «в обход» заявки на возврат запрещены.
Исключения — только аварийные процедуры с письменным разрешением owner и последующей фиксацией в audit (вне обычного процесса).
